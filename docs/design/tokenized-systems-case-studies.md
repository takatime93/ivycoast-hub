# Tokenized / Design-System Architecture — Case Studies & What Beats the Failure Modes

**Purpose:** ground our canonical design system (`DESIGN_SYSTEM.md` + `design-tokens.json`, three-tier ref→sem→cmp per W3C DTCG) not just in the happy-path structure but in the documented successes AND failures of the leading tokenized/utility systems — then convert those lessons into a concrete refinement punch-list for OUR constraints (a single hand-written `index.html`, no build step, 2 users, a token-only CSS discipline).

**Companion to:** `DESIGN_SYSTEM.md` (§1 cascade/branching, §6 composition, §7 governance), `design-tokens.json`, `design-system-charter.md`.
**Author:** Jude (iris-design) · 2026-07-13

> The one-line thesis: **the tier structure is the easy part — every serious system converged on ref→sem→cmp. What separates the systems that scale from the ones that rot is (a) a hard cap on the semantic layer, (b) an enforced "no raw values in components" rule, and (c) governance that says "no" by default.** Tailwind proves constraint-beats-freedom; the token-fatigue literature proves abstraction-without-a-cap eats itself. We already have the good bones; the refinements below are about the enforcement and the caps, which is exactly where the famous systems bled.

## 2. The cross-cutting failure modes, named — and which ones threaten US

Every system above bled from some subset of these. Ranked by **our** exposure given our constraints (single hand-written HTML file, no build/lint gate today, growing page count, 2 users):

1. **★ HIGH — Hard-coded escape hatches (our `[13px]`).** Tailwind's arbitrary-value `[13px]` is celebrated and reviled: it's the fastest way to lose consistency. In a hand-written CSS file the temptation is worse — nothing *stops* someone typing `padding:13px` or `#0e423c` (a near-miss of our `#0e413b`). We have the discipline written down (§1.2, §6.4) but **no enforcement gate**. This is our #1 risk.
2. **★ HIGH — Docs drift vs. code.** "Design and code start aligned and drift apart as sprints ship without updating both sides." Our source of truth is split across `DESIGN_SYSTEM.md`, `design-tokens.json`, AND `index.html :root` — three places to keep in sync by hand. The Appendix already lists 6 live drifts (two drawer widths, motion 300 vs 240, two scrim opacities). **Drift is already happening.**
3. **● MED — Token explosion / too many tokens.** "Thousands of derived tokens… turtles all the way down." We're small today (~20 `cmp.*`, a lean `sem.*`), but every new page pressures the semantic and component tiers. Without a **cap**, we drift toward Material's giant `comp.*` tier. The countermeasure is a stated ceiling, not vigilance.
4. **● MED — The "semantic layer that's just aliases" trap.** A semantic token is only earning its keep if it encodes **intent reused across ≥2 sites**. `sem.color.settleBg` (used by badge + calendar chip + Shipped stage + ledger) is genuinely semantic; a `sem.*` token used once is just `ref.*` with a longer name — pure over-abstraction. Some of our `sem.color.stage*`/`quality*` aliases are near this line.
5. **● MED — Over-abstraction / deep-nested names.** `color-background-surface-secondary-inverse-hover`. Our names are flat and short today (`surfaceSecondary`, not `color-background-surface-secondary`) — a real strength. The risk is *future* names creeping toward compound depth. Codify the flatness.
6. **○ LOWER — Inconsistent naming.** "When names are inconsistent, teams create duplicates of tokens that already exist." With 2 users the blast radius is small, but our names mix conventions (`primaryTint` vs `successBg` vs `stageInactiveBg` vs `sell.new.accent`). Worth a documented grammar so future additions are predictable.
7. **○ LOWER — Brittle theming.** Semantic UI's LESS theming labyrinth. Our no-build CSS-variable approach is inherently robust here — re-theme = edit `sem.*` in `:root`. Low risk, and a genuine advantage.
8. **○ LOWER — No governance → drift.** We already have §7. The gap is teeth, not existence.

## 3. How OUR ref→sem→cmp model + governance BEATS these failure modes

Concrete, tailored to no-build / single-file / 2-users. Each maps to a numbered failure mode above.

### 3.1 Beat the escape-hatch (failure #1) — a raw-value AUDIT, since we have no build lint
Tailwind restrains `[13px]` with lint plugins + a compiler that flags it. We have no compiler, so the enforcement is **a grep-based audit script + a checklist gate**, run before shipping any surface. The rule is already written (§6.4 "No raw hex in any component"); make it *executable*:
- A tiny audit (grep) that scans the `<style>` block of `index.html` for **any hex not inside `:root`**, any `px` spacing not on the ramp, any raw duration/ms outside `:root`, and any `#hex` that's a near-miss of a token (typo detection). Fails the commit hook if found. This is our version of Tailwind's arbitrary-value warning — enforced, not aspirational.
- **The near-miss check is the highest-value part:** `#0e423c` vs the real `#0e413b` is invisible to the eye and is exactly the drift Polaris/Spectrum use schema-validation to catch. We can catch it with a grep allow-list.

### 3.2 Beat docs-drift (failure #2) — collapse three sources to ONE generated pair
Right now `DESIGN_SYSTEM.md`, `design-tokens.json`, and `index.html :root` are hand-synced — three-way drift is guaranteed (the Appendix already proves it). Fix the *topology*:
- Declare **`design-tokens.json` the single machine source of truth.** Generate the `:root` CSS block from it with a ~30-line script (no framework — this is what Style Dictionary does, minus the dependency). `index.html :root` becomes **generated, never hand-edited.** That removes one entire drift axis permanently.
- The Appendix's 6 live drifts (two drawer widths, `--motion-drawer` 300 vs 240 fallback, two scrim opacities) get **reconciled once in the JSON**, then regenerated — they can't re-diverge because there's only one place to edit.
- `DESIGN_SYSTEM.md` stays the human/why layer and references token *names*, never re-states values (it mostly already does; a few tables restate hexes — point them at the token instead).

### 3.3 Beat token explosion (failure #3) — a stated CAP on each tier
The literature's fix for "turtles all the way down" is a ceiling, and Polaris/M3 restraint is the model. Put numbers in §7:
- **`ref.*`:** a value enters only if it's a genuinely new primitive (a new hue/step). Default: reuse an existing family step.
- **`sem.*`:** **cap it.** A semantic token must be consumed by **≥2 objects/sites** OR represent a named role in a closed vocabulary (status set, stage set). A one-consumer `sem.*` is a smell — inline the `ref.*` or justify it in the PR.
- **`cmp.*`:** the **expensive tier** (Spectrum/Baldwin). Add a `cmp.*` token **only** when a branch genuinely re-points it; never enumerate a component's every property speculatively. Target ceiling stated explicitly so additions feel costly.

### 3.4 Beat the "semantic-is-just-aliases" trap (failure #4) — the two-consumer rule
Adopt Baldwin's test verbatim into governance: **"a semantic token is no longer semantic when it doesn't scale across broad use cases."** Operationalize as: *a `sem.*` token must name an intent used in ≥2 places or belong to a closed role-set; otherwise it's a `ref.*` alias masquerading as meaning — delete it.* Audit our current `sem.color.stage*`/`quality*` against this and either promote them to a documented closed vocabulary (they are — the stage set, the quality set) or inline.

### 3.5 Beat over-abstraction / deep names (failure #5) — codify FLATNESS as law
Our names are already flat (`surfaceSecondary`, not `color-bg-surface-secondary`). Make it a rule so it survives us: **max 2 semantic segments** (`role` + optional `variant`), state via **suffix** (`Hover`), never compound-nested. This is the Polaris grammar (`-hover` suffix) minus the depth. It's a one-line law that prevents the `color-background-surface-secondary-inverse-hover` disease.

### 3.6 Beat inconsistent naming (failure #6) — one documented grammar
Steal Spectrum's **Context → Common-unit → Clarification** and Polaris's **state-suffix**. Write our grammar once:
- `ref.<family>.<step>` (e.g. `ref.color.ivy.900`, `ref.space.4`).
- `sem.<category>.<role><Variant?>` (e.g. `sem.color.primary`, `sem.color.surfaceSecondary`), **state as suffix** (`primaryHover`).
- `cmp.<object>.<property>` (e.g. `cmp.btnPrimary.bg`).
Then every future token is predictable — no "where does this go?" judgment call, which is precisely what the drift literature blames for duplicates.

### 3.7 Beat theming brittleness (failure #7) — keep it CSS-variable, keep the cascade one-edit
This is already our strength; protect it. Re-theme = edit `sem.*` only (§6.3). The audit (3.1) enforces that no component hard-codes, so the cascade stays real. Our no-build constraint means we **can't** grow a Semantic-UI LESS labyrinth — lean into it as a feature, not a limitation.

### 3.8 Beat governance-without-teeth (failure #8) — "no" by default + a PR checklist
Polaris publicly resists adding component tokens; make that our posture. §7 already says "default answer is no — branch or compose." Add the **teeth**: the §6.4 audit becomes a required checklist in the PR/REVIEW ticket, and adding any token requires stating (a) which tier, (b) how many consumers, (c) that it passes the grammar. If it can't answer, it's a branch or a compose, not a token.

## 4. What Tailwind gets RIGHT that we should keep adopting

Not everything is a cautionary tale — Tailwind's core insight is why the charter said "the feel is Tailwind":
- **Constraint > freedom.** You can only pick from the ramp. Our `space-*`/`size-*`/`radius-*` scales already do this; the audit (3.1) is what makes the constraint *binding* instead of *suggested* — the piece Tailwind gets from its compiler and we must get from grep.
- **Tokens as native CSS variables (v4 `@theme`).** Tailwind v4 abandoned JS config for CSS-first custom properties — converging on exactly what we already ship (`:root` vars). We're not behind here; we're at the modern endpoint with zero build cost.
- **Compose primitives, don't hand-author screens.** Our §1.3 composition rule is the utility-first mindset applied at the object tier instead of the class tier — arguably *better* for readability because it dodges Tailwind's #1 flaw (class soup): our markup names an object (`card`, `pcard`), not 14 utilities.

**Where we're structurally better than Tailwind by design:** we close its **semantic gap** (utilities describe HOW; our `sem.*` describes WHAT) and we avoid **class soup** (objects, not utility strings). Those are Tailwind's two loudest criticisms — our model is immune to both *if* the audit keeps raw values out.

## 5. Prioritized punch-list — refinements to `DESIGN_SYSTEM.md` / `design-tokens.json`

Ordered by impact-for-effort, tailored to our constraints. Items 1–3 are the ones that neutralize our two HIGH-risk failure modes.

1. **[HIGH] Ship a raw-value audit script + make §6.4 executable.** A grep audit over `index.html`'s `<style>` block: flags any hex outside `:root`, any off-ramp `px` spacing, any raw ms, and — most valuable — **near-miss hexes** vs the token allow-list. Wire it to the pre-commit hook. Converts §6.4 from a checklist into a gate. *(Beats failure #1 — escape hatches — the thing nothing currently stops.)*

2. **[HIGH] Make `design-tokens.json` the single source of truth and GENERATE `:root`.** Add a ~30-line generator (JSON → CSS custom properties) so `index.html :root` is generated, never hand-edited. Kills the three-way drift topology that the Appendix already documents. *(Beats failure #2 — drift.)*

3. **[HIGH] Reconcile the 6 live drifts in the Appendix, once, in the JSON.** Two drawer widths → one non-blocking record-drawer spec; `--motion-drawer` 300 vs 240 fallback → consume the token; two scrim opacities → one (or none on desktop). Then regenerate. These are drift *already realized* — close them before adding pages. *(Beats #2.)*

4. **[MED] Add a "Token grammar & tier caps" subsection to §7.** State: the naming grammar (§3.6), the flatness law (max 2 semantic segments, state-as-suffix — §3.5), and the **two-consumer rule** for `sem.*` + the "cmp.* is the expensive tier" posture (§3.3–3.4). This is the single edit that inoculates us against token explosion as page count grows. *(Beats #3, #4, #5, #6.)*

5. **[MED] Audit existing `sem.*` against the two-consumer rule.** Confirm `stage*`, `quality*`, `sell.*`, `eventTint.*` each either serve ≥2 sites or are documented closed vocabularies (they are — annotate them as such in the JSON `$description`), and inline any true single-use alias. Prevents the "semantic = aliases" smell from setting in. *(Beats #4.)*

6. **[MED] Add a governance "teeth" checklist to the REVIEW ticket template.** Any new token/object PR must answer: tier? consumer-count? passes grammar? is it a branch/compose instead? Default = no. Make §7.1's "default answer is no" a form you fill, not a value you hold. *(Beats #8.)*

7. **[LOW] Add a "What we deliberately reject" note citing the case studies.** One short §: we reject arbitrary-value escape hatches (Tailwind), heavy toolchain theming (Semantic UI/LESS), and speculative component tokens (Spectrum/M3 sprawl) — with the two-consumer + audit rules as the countermeasures. Makes the *why* legible to future contributors and stops re-litigating.

8. **[LOW] Add `$deprecated` support + a "how to remove a token" step to §7.** The governance literature flags "deprecating old ones" as the missing half of most governance. Even at 2 users, a stated removal path (mark `$deprecated`, grep for consumers, remove) prevents zombie tokens. *(Beats #3/#8.)*

The entire remaining risk is **enforcement**: the systems that rotted didn't lack tiers, they lacked a cap and a gate. Our refinements are almost all about adding teeth (an audit, a generator, a two-consumer rule) rather than restructuring — which is the right, cheap move for 2 users.
